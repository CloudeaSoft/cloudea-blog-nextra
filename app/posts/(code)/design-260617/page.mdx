这两天进行了公司 ERP 的权限系统的设计, 中间比较曲折, 最后安全落地.

## 背景

公司正在从零自研一款 ERP 软件, 我负责的是整个系统的**用户与权限模块**. 这是项目的基础设施级模块, 几乎所有后续业务功能都依赖它来做访问控制, 因此设计的合理性会直接影响整个项目的开发效率和交付质量.

权限系统的设计从启动到最终定稿, 经历了 **4 个版本的推倒重来**, 中间涉及与前端, 技术主管的多轮碰撞. 整个过程谈不上顺利, 但最终安全落地.

这篇复盘记录的不是"我做了多好的设计", 而是**我是如何一步步发现自己想错了的**.

## 约束条件

在开始设计之前, 先明确我们面对的限制条件:

| 约束维度     | 具体内容                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------- |
| 技术栈       | 基于 Django 自带的 `auth` 模块 (User, Group, Permission) 进行扩展, 不引入第三方权限框架                         |
| 组织模型     | 公司 → 部门 → 员工, 三级结构. 账号分三个大级别: 超级管理员, 部门主管, 部门成员                                  |
| 权限分配方式 | 分两类: **固定权限** (长期有效, 由超管分配给部门, 或由主管分配给部门成员) 和**临时权限** (短期授予, 直接给账号) |
| 权限类型     | 分两种: **路由权限** (控制菜单/页面可见性) 和 **API 权限** (控制后端接口可调用性) , 核心目标是保证访问安全      |
| 用户规模     | 使用人数有限 (数十人级别) , 通过部门能自然分摊管理成本                                                          |

这些约束共同指向一个核心命题: **在有限的技术选型和组织规模下, 如何设计一套既能让管理员高效分配权限, 又能保证访问安全的系统？**

下面就是我在这道命题上反复试错的 4 个版本.

## 四次演进

### 第一版

第一版由我独立设计, 核心思路是:

1. 用户的权限获取分**两条路**:
   - **部门岗位固定权限**: 用户属于某个部门时, 自动获得该部门岗位对应的基础权限
   - **动态权限组**: 额外给用户单独绑定临时权限或特殊权限

2. 在路由权限上, 我和前端产生了讨论——前端希望后端动态生成路由, 而我坚持用静态配置菜单项

最终我认可了前端的方案, 理由是:

- 前端可以更灵活地控制菜单的显示.
- 后端只需要提供一个菜单配置接口即可, 不需要额外维护菜单配置.
- 项目将部署在公网, 仅生成必要路由能提升安全性.

### 第二版

用户权限的获取分两条路, 但直接用固定的2个Group来指代部门内的两级权限

主管提出可以将每个菜单项直接绑定到对应的api上, 这样就可以直接使用django自带的Permission了

框架提供的 Permission 细粒度到 API 在理论上是完美的, 但在业务场景中过细反而导致管理成本爆炸

### 第三版

与技术主管深入交流后, 第三版做了大幅简化:

- 放弃复杂的 Group 继承关系, 将权限直接绑定到用户
- 简化权限获取逻辑: 用户拥有什么权限, 直接查用户关联的权限记录即可

这次修正源于:

- 使用人数有限(数十人级别), 不需要分布式级别的扩展性
- 部门能分摊管理成本, 每个主管只管自己部门那几个人
- 即便有性能问题, 加一层缓存就能解决, 没必要为了"未来的性能"提前把模型搞复杂
- 实际工作中用户更关注页面而不会关注真实的API到底是什么, 所以大多情况下都是一组一组给成员分权限的, 关键的删除操作等他们也能记住额外配置.

我考虑将用户的权限与部门绑定在一起, 这样分配的时候才能有正确的分配逻辑, 否则当用户存在于多个部门时, 分配权限会产生冲突.

### 第四版

最终版本的核心变更:

- 用户直接关联菜单, 在关联菜单时**同步写入**菜单绑定的API权限与用户的关联
- 将部门, 主管等概念从权限系统中剥离, 不再做任何过滤计算, 直接使用用户身上的权限记录

在最后交流时, 我发现我忘记了之前沟通过的一个重要前提: 管理员的认知模型就是"菜单等于权限组"

基于这个前提, 正确的做法是:

- 管理员给用户分配权限时, 界面操作是"勾选菜单"
- 后端在保存时自动完成两件事: 建立"用户-菜单"关系 + 同步写入"用户-API权限"关系
- 查询时直接读用户身上的权限记录, 不需要再通过部门, 岗位, Group 等中间层做任何计算

我一味追求数据库的规范化, 觉得"权限应该存在一个地方, 通过关联关系推导出来", 结果反而让系统变得笨重且难以理解. 管理员要分配一个权限, 要经过 "用户→部门→岗位→权限" 四层推导, 中间任何一层出问题都会导致权限失效.

更关键的是: **管理人员更希望做简单重复的操作, 而不是去理解复杂的模型关系**

他们每天要做的是"给新来的小王分配销售部的菜单权限", 而不是"理解RBAC模型然后手工维护外键关系". 既然他们的操作就是"勾选菜单", 那么数据库里就应该直接存"用户-菜单"的关系, 而不是通过中间表推导出来.

## 总结

回顾四个版本, 我的错误可以归结为三个字: **想太多**.

一开始想着权限模型要足够灵活, 以后所有子系统都能接入. 但公司就一个ERP, 没有"以后". 我为不存在的东西预支了复杂度, 设计了岗位权限和动态权限组两条路, 技术上解耦了, 管理员却分不清什么算岗位的, 什么算临时的.

后来掉进框架陷阱, 觉得用 Django 原生 Group 和 Permission 就是最佳实践. 但 Permission 细到单个API, 管理员根本不看API, 只看菜单. 结果就是我自己用着爽, 管理员用着懵.

再后来意识到用户在多部门时权限归属会冲突. 这个发现是对的, 但我还在纠结"权限挂在哪里", 本质上仍在追求完美的存储模型.

绕了一大圈才想通最朴素的道理: 管理员每天做的事就是"给小王勾几个菜单". 他要的是打开页面, 找到小王, 勾选"销售订单管理", 点保存, 完事.

最终方案极其直白: 直接存"用户-菜单"关系, 保存时自动把菜单绑定的API权限一并写入. 查询时直接读用户身上的权限记录, 不再经过部门, 岗位, Group 任何中间层. 有冗余没关系, 写入逻辑保证一致性, 冗余换来的就是"三秒完成分配".

这件事教会我的: **先想"谁在用, 怎么用", 再想"表怎么建".** 操作路径是什么, 数据模型就怎么建. 一个普通主管能在三次点击内完成分配, 比任何优雅的ER图都重要.

另外两个落地层面的体会: 数据库是难修改的, 重构时牵一发动全身, 设计阶段就要多推敲; 尽量在文档期对齐关键点, 避免后续反复沟通消耗时间.
